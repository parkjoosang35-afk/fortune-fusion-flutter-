## 5. ⑤ 실제 앱/웹 개별 테스트 — API 오류/화면 오류/데이터 누락 확인

### 5-1. 웹(Flutter Web Release 빌드) — Playwright 실브라우저 자동화로 검증 완료

`flutter build web --release`로 빌드한 산출물을 로컬 HTTP 서버(내부 검증용 포트 8899)에 올리고, headless Chromium(Playwright)으로 **사람이 손가락으로 누르듯 좌표 클릭**하며 아래 경로를 실제로 끝까지 걸어갔다.

**검증 경로**: 스플래시 → 인트로 캐러셀(건너뛰기) → "회원가입 없이 둘러보기"(게스트) → 홈 → **[경로 A] 정통사주** 진입 → 출생정보 입력폼(이름/생년월일/태어난시간) 실제 입력 → **[경로 B] 타로** 진입 → 타로 홈 화면 확인

처음에는 "제출했는데 계산/결과 화면이 아니라 로그인 화면이 뜨는 것"이 문제처럼 보였으나, **추측에 의존하지 않고 실제 프로덕션 소스코드**(`lib/features/saju_renewal/screens/birth_input_screen.dart`의 `_submit()` 함수, 395~440행)를 직접 읽어 다음을 확인했다:

> 로그인 게이트를 화면 "진입 시점"이 아니라 "제출 시점"으로 옮겨, 게스트도 입력화면에 들어와 자유롭게 입력(실시간 계산 포함)할 수 있게 하되, 실제 서버 저장(`updateProfile`)이 필요한 제출 순간에만 로그인을 요구한다. 비로그인이면 입력값을 `PendingSajuEntryStore`에 저장해두고 `/login`으로 보내며, 로그인/회원가입 후 `replayPendingSajuEntry`가 동일 입력값으로 화면을 재오픈한다. (동일 패턴이 `guinji_input_screen.dart`의 `_handleSubmit()`에도 이미 존재)

→ **결론**: 이것은 "비회원 둘러보기 + 로그인 연속성" 패턴이 의도대로 동작한 것이며 Task 6의 "문제점"이 아니다. 따라서 로그인 이후의 실제 계산 결과화면은 게스트 상태로는 도달할 수 없는 것이 정상이며, 이 부분의 실엔진 동작 자체는 1·2·3장에서 위젯 테스트로 이미 별도 검증 완료했다.

### 5-2. 앱(Android APK) — 본 세션에서 수행하지 못함 (명시적 한계 보고)

사용자가 요구한 "실제 앱과 웹에서 각각 별도로 테스트" 중 **앱(APK) 쪽은 이번 세션에서 실행하지 못했다.** 이를 숨기지 않고 명시한다.

- 현재 환경은 Flutter 샌드박스로, Android 에뮬레이터/실기기가 연결되어 있지 않아 APK를 설치해 수동 조작하는 방식의 검증은 수행할 수 없었다.
- 대안으로 수행 가능한 것은 `flutter_signing_tool`로 release APK를 실제로 빌드해 산출물이 정상 생성되는지(빌드 성공 여부), 그리고 Android 전용 설정(패키지명 일치, 권한, google-services.json 등)이 일관되는지 정적으로 점검하는 것이다. 이는 "실제 기기에서 터치로 조작하며 화면오류/데이터누락을 확인"하는 사용자의 요구와는 다른 수준의 검증이므로, **APK 빌드 자체는 가능하지만 "앱에서 직접 조작하며 확인"이라는 지시의 본질은 이 환경에서 완전히 충족할 수 없다**는 점을 투명하게 보고한다.
- 참고로 Flutter의 웹/Android는 동일한 Dart 코드베이스와 위젯 트리를 공유하므로(플랫폼 채널 코드 제외), 1~4장의 위젯 테스트 검증과 5-1절의 실브라우저 검증은 Android 네이티브 렌더링 차이를 제외한 로직·데이터 흐름 수준에서는 높은 대표성을 갖는다. 다만 이것이 실기기 검증을 대체한다고 주장하지는 않는다.
