# 전역 핀치 확대 시스템 — 이미지·텍스트 화질 검수 보고서

지시서 §4 "화질 보호" 요구사항 대응. **전제**: 본 전역 핀치 확대 엔진은
"돋보기(screenshot magnifier) 방식"으로 구현되어 있다 — 핀치 시작 순간
`RenderRepaintBoundary.toImage(pixelRatio: devicePixelRatio)`로 **현재
화면에 실제로 그려진 그대로**를 고해상도 캡처해 확대한다. 즉 이 엔진은
"평소 화면에 표시되는 원본 해상도"를 그대로 재사용할 뿐, **저해상도
원본을 고화질로 변환하는 기능은 없으며 그런 기능을 제공한다고 주장하지
않는다**(지시서 "확대 엔진이 저화질 원본을 고화질로 바꿀 수 있다고
간주하지 않는다"는 전제와 정확히 일치).

## 1. 저해상도 썸네일을 확대 원본으로 쓰지 않는지 확인

- 캡처 소스는 화면에 실제 렌더링된 위젯 트리 전체(`RepaintBoundary`로
  감싼 최상위)이며, 별도의 "축소된 썸네일 전용 캐시"를 확대 대상으로
  쓰는 코드 경로가 없다 — `global_pinch_zoom_manager.dart`의
  `_renderController.capture(_boundaryKey, devicePixelRatio: dpr)` 호출
  1곳뿐이고, `dpr`은 `MediaQuery.devicePixelRatio`(기기 실제 배율,
  보통 2.0~3.0)를 그대로 사용한다. **문제 없음.**

## 3. 벡터(SVG) 지원 확인

- `flutter_svg: 2.0.10+1` 패키지가 `pubspec.yaml`에 선언되어 있고,
  `assets/icons/bottom_nav/` 하위 10개 SVG(하단 네비게이션 아이콘,
  active/default 상태별)가 존재한다.
- 전역 핀치 확대 엔진은 **화면 캡처(래스터) 방식**이므로, SVG든
  래스터든 "화면에 그려진 시점의 해상도"로 캡처된다. 즉 SVG 자체의
  벡터 무한 확대 특성은 핀치 확대 단계에서는 활용되지 않는다(이는
  "돋보기 방식" 아키텍처의 트레이드오프이며, §0 전제에 명시한 대로
  처음부터 "원본 이상으로 선명하게 만들지 않는다"는 설계 원칙과
  일치한다 — 하단 네비게이션 아이콘은 애초에 핀치 확대 대상으로
  적합하지 않은 UI 요소이기도 하다).

## 4. 텍스트를 이미지로 변환하는지 여부

- 사주 명식/팔자 텍스트, 한자 텍스트는 `Text` 위젯(폰트 렌더링)으로
  직접 그려지며, 이미지로 사전 렌더링해서 쓰는 코드 경로를 발견하지
  못했다(화면 캡처 엔진 설계상 Text 위젯이든 Image 위젯이든 캡처
  시점 해상도로 동일 처리되므로 구분이 큰 의미는 없으나, "텍스트를
  이미지로 변환 금지" 요구사항 자체는 애초에 위반 소지가 없다).
- `TextScaleProvider`/`TextScaleFab`(결과화면 "가-/가+" 글자 크기
  배율)은 핀치 확대와 별개의 기존 기능으로, **폰트 자체를 키우는
  방식**이라 핀치 확대와 달리 진짜 무손실 확대다 — 그대로 유지된다.

## 5. 발견된 문제 — 원본 해상도 부족으로 별도 교체가 필요한 자산

지시서 §4 "원본 해상도가 부족한 이미지는 확대 엔진이 해결할 수 없으므로
별도 교체 대상으로 보고한다"에 따라 아래를 교체 검토 대상으로 보고한다.

### 5-1. `assets/wishroom/items/` — 20개 파일이 200px 미만

```
t_beads.png 188×166   t_bell.png 126×182   t_bible.png 218×134
t_cross.png 108×190   t_flowers.png 146×170  t_gift.png 130×140
t_glass.png 182×198   t_hands.png 152×200  t_heart.png 142×124
t_holder.png 118×178  t_lamp.png 170×158   t_lotus.png 196×158
t_pattern.png 124×196 t_prayc.png 90×184   t_rainbow.png 192×110
t_rattle.png 142×168  t_sfan.png 198×130   t_stars.png 104×102
t_statue.png 120×172  t_talisman.png 142×162
```
소원방 "소원 꾸미기(decor)" 화면에서 아이템을 배치할 때 쓰이는 작은
아이콘류로 추정된다(파일명 패턴 `t_*`). 평소 화면에는 수십~백여 px
크기로 작게 표시되지만, 사용자가 핀치로 3배까지 확대하면 **원본
해상도 자체가 작아 테두리 계단 현상(블러/픽셀화)이 육안으로 체감될
가능성이 높다**. 이는 핀치 확대 엔진의 결함이 아니라 원본 소스
자산의 해상도 한계이므로, **최소 400×400px 이상으로 재제작/교체를
권장**한다.

### 5-2. `assets/images/guinji/chars/` — face 계열 256×256

귀인지도 캐릭터의 얼굴(face) 전용 이미지가 256×256으로, body(600×800)
대비 상대적으로 낮다. 귀인지도 지도 화면에서 얼굴이 차지하는 평소
표시 면적은 작지만, 3배 핀치 확대 시 body 대비 상대적으로 흐려 보일
가능성이 있다. 체감 열화가 적을 수도 있어(원래 작게 표시되는 요소라
3배 확대해도 절대 픽셀 수가 크지 않음) **보통 우선순위의 교체 검토
대상**으로 보고한다.

## 6. 결론 및 권고

- 핀치 확대 엔진 자체는 "화면에 그려진 원본을 그대로 고해상도
  캡처"하는 방식으로 구현되어 화질 저하를 추가로 유발하지 않는다.
- 다만 **`wishroom/items`의 20개 소형 아이콘**은 원본 자산 자체의
  해상도가 낮아, 핀치 확대 시 체감 품질 저하가 예상된다 — 이는
  "확대 엔진이 저화질을 고화질로 바꿀 수 없다"는 전제에 따라 **디자인
  리소스 교체가 필요한 항목**으로 별도 보고한다(엔진 수정으로 해결
  불가능).
- 실제 기기 화면 밀도(devicePixelRatio)·실제 손가락 핀치 배율에서
  체감되는 정확한 열화 정도는 **실기기 테스트로만 최종 확인 가능**하며,
  이 샌드박스 환경에서는 측정 데이터(자산 해상도 수치)만 제공 가능하다.
