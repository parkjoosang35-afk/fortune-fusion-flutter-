# 인계 문서 미완료항목 5·6·7 — 코드방 정적 감사 결과 (2026-10-14)

작성 기준: 신통방통_코드방_개발인계_20261014.md §6 항목 5/6/7
방법: 정적 코드 리딩 + `flutter test`(자동 시험) 커버리지 확인.
**주의**: 아래는 전부 정적 분석 결과다. 실제 기기 설치·실제 브라우저 조작으로만
확인 가능한 항목(카카오 PNG 실제 수신, 갤러리 권한 실제 거부 UX, 웹 링크 실제
클릭 등)은 "미검수"로 유지한다 — 이 문서가 그 실사용 검수를 대체하지 않는다.

## 1. 공유·저장(§6-5) 호출 경로 정적 확인

### 1-1. ShareService.shareResult() 호출부 전수 목록 (9곳)
grep 기준 `ShareService.shareResult(` 호출부:
- face_result_screen.dart, palm_result_screen.dart, tarot_result_screen.dart,
  story_detail_screen.dart(사주), complete_screen.dart(소원방),
  guinji_deep_result_screen.dart, guinji_map_relation_detail_screen.dart,
  guinji_result_card_screen.dart — 7개 실제 결과 화면 + full_result_sheet.dart
  (공유받은 화면의 재공유 경로).

각 화면의 `originalResultKey`/`sourceRefId` 전달 여부를 대조한 결과:
- face/palm/tarot/사주/소원방: `originalResultKey` + `sourceRefId` 모두 전달.
- guinji_map_relation_detail_screen, guinji_result_card_screen: `originalResultKey`
  전달.
- guinji_deep_result_screen: `originalResultKey`를 넘기지 않고 `preCapturedPng`를
  직접 전달하는 방식 — `_captureFullPagePng()`로 화면 자체 캡처 후 결과만
  넘기므로 ShareService 내부에서 다시 캡처할 필요가 없어 **의도된 설계**임을
  확인(버그 아님).

결론: originalResultKey/sourceRefId 지정 범위는 인계 문서가 밝힌 대로 현재
7개 핵심 결과 화면에 통합되어 있으며, 누락처럼 보였던 guinji_deep_result_screen은
preCapturedPng 경로라 정상이다.

### 1-2. 홈페이지 공유 버튼(shareWebPage) 연결 범위
`ShareService.shareWebPage()` 실제 호출부는 **`full_result_sheet.dart` 1곳뿐**
(웹 플랫폼에서 "링크 전송" 버튼을 누를 때)이다. 인계 문서 §2 "모든 화면에
홈페이지 공유 버튼을 새로 연결한 것은 아니다"라는 서술과 정확히 일치 —
새로운 미연결 지점을 발견하지 못했다(이미 알려진 제한 범위 그대로임을 재확인).

### 1-3. 저장(갤러리/다운로드) 공통 경로
`saveImageBytesToGallery()`(io/web 분기) 호출부 4곳:
guinji_deep_result_screen, guinji_result_card_screen, full_result_sheet,
wallpaper_screen. 공통 함수 자체가 `bytes.isEmpty` 체크로 빈 이미지 저장을
차단하고(§2 "빈 이미지 저장 차단"과 일치), 각 호출부는 실패 시
`throw StateError(...)` → catch에서 사용자에게 실패 메시지를 보여주는 패턴을
일관되게 따른다. 성공 시 메시지도 플랫폼별(`kIsWeb` 분기)로 "다운로드 요청했어요"
/"갤러리에 저장했어요"를 구분해 "다운로드 완료를 확인한 것처럼 안내하지
않는다"(§2-6) 원칙을 지키고 있다.

### 1-4. 초대 링크 vs 결과 공유 분리
`shareLink()`(소원방 S1, `/wish-rooms/{id}/share-link`)와
`buildGuinjiInviteLink()`(귀인지도 참여 토큰 링크)는 `ShareService.shareResult`/
`shareWebPage`와 코드 경로가 완전히 분리되어 있다 — §2-4 "초대 공유: 기존 참여
링크 유지, 결과 공유와 혼동해 변경하지 않는다"는 원칙이 실제로 지켜지고 있음을
확인(두 기능이 같은 함수를 공유하지 않음).

### 1-5. 자동 테스트 커버리지
공유·저장 관련 기존 자동 테스트 9개 확인:
app_image_share_test, full_result_share_test, gallery_permission_flow_test,
guinji_share_link_cache_bust_test, original_result_capture_test,
received_result_image_share_test, safe_share_outcome_test,
share_environment_test, share_system_contract_test — 취소/미지원/실패 분기,
갤러리 권한 분기가 이미 자동 시험으로 커버되어 있다(§5 "권한 분기 시험"과 일치).
**단, 이들은 모두 시뮬레이션(mock) 기반 위젯 테스트이며, 실제 카카오톡 OG 렌더링,
실제 기기 갤러리 저장, 실제 브라우저 다운로드 완료는 검증하지 않는다 — 이 부분은
여전히 "미검수"다.**

## 2. 사주 전체 흐름(§6-6) 정적 확인

- birth_input_screen → calculating_screen → analysis_complete_screen/
  story_preview_screen → story_detail_screen 흐름을 따라가며 각 단계의
  `SajuRenewalProvider` 상태 전이(loading/error/storyPreview/complete)를 확인.
- error_screen.dart가 "입력 오류"(성별/생년월일 누락 → 입력 화면으로 유도)와
  "네트워크 오류"(재시도 버튼 → `provider.retry()`)를 분기 처리하며, 입력 화면에서
  돌아오면 `addPostFrameCallback`으로 자동 재시도하는 로직을 확인 — 사용자가
  재시도 버튼을 또 누를 필요가 없도록 설계되어 있음.
- story_detail_screen의 "결과페이지 그대로 저장" 버튼은 공통
  `saveOriginalResult()`를 호출하며 위 1-3과 동일한 실패 안내 패턴을 따른다.
- 이 흐름 전체에 대한 실제 서버 응답(실사용 해석 생성) 기반 종단 테스트는
  리포지토리에서 발견하지 못했다 — 즉 "해석 생성 실사용" 자체는 정적 분석으로
  보증할 수 없고, 인계 문서가 명시한 대로 실사용 검수가 필요하다(미검수 유지).

## 3. 전체 호출 감사(§6-7) — 금번 라운드 추가 확인

- `ShareService.shareResult`/`shareWebPage`/`shareImageDirectly` 세 공개
  메서드의 모든 호출부를 grep으로 전수 조사(위 1-1, 1-2) — 신규 누락 지점을
  발견하지 못함.
- 저장 경로(`saveImageBytesToGallery`, `saveOriginalResult`) 전수 호출부 확인
  — 일관된 실패/성공 안내 패턴 확인.
- 귀인지도 ownerFace 서버 동기화(§6-3)는 이번 세션에서 서버
  `admin_web/prisma/schema.prisma`의 `GuinjiMap` 모델을 직접 확인한 결과
  ownerFace 관련 컬럼이 전혀 없음을 재확인 — 로컬(SharedPreferences) 저장만
  구현되어 있으며, 다른 기기 동기화는 서버 스키마 마이그레이션부터 필요한
  별도 개발 범위임을 명확히 함(코드방 범위의 "버그 수정"이 아님).

## 4. 결론 및 검수표 갱신 제안

이번 라운드는 **정적 코드 감사**이며 아래 항목은 여전히 "미검수"로 유지해야
한다(실제 기기·브라우저 조작 필요):
- 카카오 PNG 실제 수신 확인
- 갤러리 권한 실제 거부 시 UX
- 웹 링크 실제 클릭 → 전체 다운로드 확인
- 사주 해석 생성 실사용(서버 실응답) 흐름

반대로 이번 라운드에서 "코드 경로 자체의 결함"은 추가로 발견되지 않았다 —
기존 인계 문서가 설명한 범위와 실제 코드가 일치함을 재확인한 것이 핵심
성과다.
